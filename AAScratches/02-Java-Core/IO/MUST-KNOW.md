## Full practice order


### A — Building blocks

- `A01_InputOutput.java` — Scanner read single int
  - The smallest possible I/O primitive - open Scanner on System.in, read one token as int; everything else in the folder assumes you can do this without thinking.
- `A02_ScannerMain.java` — Scanner token loop, next vs nextInt
  - Extends the single read into a fixed-count token loop and sits exactly on the next()/nextInt()/nextLine() mixing trap, which is the first place naive input code breaks.

### C — Medium

- `C01_CsvReader.java` — BufferedReader streaming into a thread pool **[must-know]**
  - First file-backed problem: streams line by line so memory stays flat, then hands each record to an ExecutorService with an AtomicLong counter - the read-side half of every large-file question, and the pattern CsvAppender's write side mirrors.

### D — Hard

- `D01_CsvAppender.java` — Lock-serialised concurrent file append
  - Hardest here because the obvious answer is wrong: 10 threads plus a global ReentrantLock and a FileWriter reopened per record serialise anyway and thrash the disk; the non-obvious insight is one writer thread behind a bounded queue with batched buffered writes, which you can only argue once CsvReader's streaming model is in place.

## Interview readiness

This folder is deep on exactly one axis and empty on every other. The four files total under 7KB, and two of them (InputOutput, ScannerMain) are five-line Scanner demos. The real content is CsvReader/CsvAppender, and through them he has genuinely internalised the concurrency-and-throughput axis of file I/O: streaming with BufferedReader, fan-out to an ExecutorService, why an unbounded submit loop needs a bounded queue rather than more threads, lock-vs-single-writer-thread for one shared file, and the cost of reopening a FileWriter per record. That is a strong, senior-sounding story and it will carry the first ten minutes of an I/O question. What is missing is everything that is not about threads. There is no memory-bounded algorithm on a file at all — no top-K word count, no external merge sort — so the moment an interviewer says "the file is 200GB and the map does not fit in heap," he has nothing rehearsed. There is no encoding awareness: his own CsvReader opens with `new FileReader(CSV_FILE)` and CsvAppender writes with a bare `new FileWriter(...)`, both platform-default charset, which is the single easiest thing for a staff interviewer to pick at in code he wrote himself. There is no java.nio.file anywhere in the folder, which reads as pre-Java-7 muscle memory in 2026. And his CSV work never actually parses a CSV — it counts lines and concatenates strings, so the standard follow-up ("now a field contains a comma inside quotes") is unpracticed. Net: he would pass a mid-level I/O screen comfortably and stall on the senior/staff follow-ups, because the follow-ups all leave the concurrency axis he has covered. Four targeted problems (top-K, external sort, charset, NIO.2) would close most of the gap.
