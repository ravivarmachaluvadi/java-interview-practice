## 1. Explain records in Java. How are they different from Lombok-annotated classes?

Records are an **immutable data carrier** — that is, they are meant to hold data without boilerplate code.

Quick facts:

| Question | Answer |
| --- | --- |
| Can a record extend an abstract class? | No |
| Can a record implement interfaces? | Yes |
| Can a record be `sealed` or a permitted subclass? | Yes |
| What is every record's superclass? | `java.lang.Record` |

```java
public record Employee(String id, String name, int age) {}
```

This single line of code automatically gives you:

- A final class (`Employee` can't be extended)
- Private final fields for each component (`id`, `name`, `age`)
- A canonical constructor (`public Employee(String id, String name, int age)`)
- Accessors (not getters, but same purpose) → `id()`, `name()`, `age()`
- `equals()`, `hashCode()`, and `toString()` implementations

Example with a compact constructor and a custom method:

```java
public record Employee(String id, String name, int age) {
    public Employee {
        if (age < 18) {
            throw new IllegalArgumentException("Age must be >= 18");
        }
    }
    public String greeting() {
        return "Hello, " + name;
    }
}
```

### Record vs Lombok

| Aspect | Java Record | Lombok (`@Data`, `@Value`, etc.) |
| --- | --- | --- |
| Boilerplate Reduction | Built into language | Via annotation processing |
| Mutability | Always immutable | Can be mutable or immutable depending on annotation |
| Inheritance | Final (cannot extend) | Can extend other classes |
| Equals / HashCode / ToString | Auto-generated by compiler | Auto-generated by Lombok |
| Constructor | Canonical constructor auto-generated | Lombok generates all-args or no-args based on config |
| Reflection / Pattern Matching | Supported in modern Java syntax (e.g., pattern matching `instanceof`) | Just a normal POJO under the hood |
| Dependency | Pure Java feature (no dependency) | Requires Lombok (annotation processor) |
| Readability | Very concise and explicit | Still somewhat verbose compared to records |

### When I still use Lombok

Even today, I still use Lombok when:

- I need mutable entities (like JPA entities where setters are required)
- I want builder patterns (`@Builder`) for object creation flexibility
- I'm on Java 8 or 11 where records aren't available

## 2. What are the disadvantages of using records in Java?

### Cannot extend other classes

- All records implicitly extend `java.lang.Record`.
- Hence, inheritance from other classes is not allowed.
- You can only implement interfaces.

Example:

```java
class Base {}
record Derived(int x) extends Base {} // Not allowed
```

This limits their use in hierarchies that depend on polymorphic behavior.

## 3. Can a record extend another class?

No — records implicitly extend `java.lang.Record`, and Java doesn't support multiple inheritance, so they cannot extend any other class.

However, records can implement interfaces.

Example:

```java
public record Point(int x, int y) implements Comparable<Point> {
    public int compareTo(Point o) {
        return Integer.compare(this.x, o.x);
    }
}
```

## 4. Can you define instance fields in a record other than the components?

Yes, but only static fields can be added — instance fields other than record components are not allowed.

Example (valid):

```java
public record Employee(String id, String name) {
    static int employeeCount = 0; // allowed
}
```

## 5. Can you override constructors in a record?

Yes — records support two forms of constructors:

- **Canonical constructor** — takes all components in the declared order.
- **Compact constructor** — no parameter list, allows validation or preprocessing.

Example:

```java
public record Employee(String id, String name, int age) {

    // Compact constructor
    public Employee {
        if (age < 18) throw new IllegalArgumentException("Invalid age");
    }
}
```

You can also explicitly define the canonical constructor:

```java
public Employee(String id, String name, int age) {
    this.id = id.trim();
    this.name = name;
    this.age = age;
}
```

A non-canonical constructor delegating to the canonical one:

```java
public record Employee(String id, String name, int age) {

    // Non-canonical constructor delegating to canonical one
    public Employee(String name) {
        this("UNKNOWN", name, 30);
    }
}
```

## 6. Are record fields truly immutable?

The fields of a record are `final`, but that does not guarantee deep immutability.

If you need true immutability, wrap or copy mutable objects inside the constructor:

```java
public Employee(String name, List<String> skills) {
    this.name = name;
    this.skills = List.copyOf(skills);
}
```

## 7. Can a record have methods other than accessors?

Yes — records can have custom instance methods, static methods, and nested classes.

Example:

```java
public record Point(int x, int y) {
    public double distance(Point other) {
        return Math.hypot(x - other.x, y - other.y);
    }
}
```

You can also override `toString()`, `equals()`, etc.

## 8. Can you use records with frameworks like JPA or Hibernate?

Not recommended — JPA expects no-arg constructors and mutable entities (via setters), which records do not support.

Records are better suited for:

- DTOs
- API requests/responses
- Event models (Kafka, messaging)

## 9. Trick question: can a record have an inheritance hierarchy with other records?

No. Records cannot extend another record or class, but they can implement interfaces.

This is because every record extends `java.lang.Record` implicitly, and Java allows only single inheritance.

However, you can simulate polymorphism via sealed interfaces (see [Explain sealed classes](#10-explain-sealed-classes)).

## 10. Explain sealed classes

In short — sealed classes give you controlled inheritance.

```java
sealed interface Payment permits CreditCardPayment, UpiPayment, CryptoPayment {}

final class CreditCardPayment implements Payment {}
final class UpiPayment implements Payment {}
non-sealed class CryptoPayment implements Payment {} // Allow future extensions
```

The same idea with a sealed abstract class:

```java
public sealed abstract class Payment permits CreditCardPayment, UpiPayment, WalletPayment {
    public abstract void process();
}

final class CreditCardPayment extends Payment {
    @Override
    public void process() {
        System.out.println("Processing credit card payment...");
    }
}

final class UpiPayment extends Payment {
    @Override
    public void process() {
        System.out.println("Processing UPI payment...");
    }
}

final class WalletPayment extends Payment {
    @Override
    public void process() {
        System.out.println("Processing wallet payment...");
    }
}
```

## 11. Can an enum extend a sealed class?

No. Enums cannot extend any class (they implicitly extend `java.lang.Enum`).

But a sealed interface can be implemented by an enum.

## 12. Can a record be a permitted subclass of a sealed class?

Yes, because record classes are implicitly final.

Example:

```java
public sealed class Shape permits Circle, Rectangle {}
public record Circle(double radius) extends Shape {}
public record Rectangle(double w, double h) extends Shape {}
```

This pattern is common for immutable data hierarchies.

## 13. Explain pattern matching

Pattern Matching in Java is a language feature introduced progressively (since Java 14) to make code involving type checks and conditional logic more concise, safe, and readable.

### Pattern matching for `instanceof` (Java 16+)

Java improved this with pattern matching for `instanceof`:

```java
if (obj instanceof String s) {
    System.out.println(s.toUpperCase());
}
```

### Pattern matching with `switch` (Java 17+ preview, Java 21 stable)

Pattern matching was extended to switch expressions, allowing more expressive data-driven logic.

Example:

```java
static String format(Object obj) {
    return switch (obj) {
        case Integer i -> String.format("int %d", i);
        case Long l    -> String.format("long %d", l);
        case String s  -> String.format("String '%s'", s);
        case null      -> "null value";
        default        -> obj.toString();
    };
}
```

Now you can handle multiple patterns in one place — much like modern pattern matching in Scala or Kotlin.

### Real-world example

In one of our microservices, we had multiple event types arriving through Kafka — like `UserCreatedEvent`, `OrderPlacedEvent`, etc.

Earlier we had an ugly if-else chain:

```java
if (event instanceof UserCreatedEvent) { ... }
else if (event instanceof OrderPlacedEvent) { ... }
```

After adopting pattern matching with switch (Java 21), we wrote:

```java
String result = switch (event) {
    case UserCreatedEvent u -> handleUserEvent(u);
    case OrderPlacedEvent o -> handleOrderEvent(o);
    case PaymentFailedEvent p -> handlePaymentEvent(p);
    default -> throw new IllegalArgumentException("Unknown event: " + event);
};
```

Benefits:

- Cleaner, type-safe
- No manual casting
- Easier to extend for new event types

## 14. Can you use multiple patterns in one switch case?

Yes — Java supports guarded patterns and OR patterns:

```java
return switch (obj) {
    case Integer i when i > 0 -> "Positive Integer";
    case Integer i when i < 0 -> "Negative Integer";
    case String s, null -> "String or Null";
    default -> "Something else";
};
```

- Useful for complex branching without nested if-else.
- Cleaner and safer than imperative chains.

## 15. Is pattern matching syntactic sugar or does it affect runtime performance?

It's syntactic sugar — compiled down to traditional `instanceof` checks and casts.

But it:

- Simplifies the code
- Improves readability
- Enables compile-time type inference
- Has no runtime overhead (identical bytecode optimization)

So, pattern matching improves developer ergonomics, not raw performance.

## 16. Explain switch expressions and their latest features

### Switch as an expression (yielding a value)

The old `switch` was a statement; the new one can be an expression returning a value.

Example:

```java
int numLetters = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> 6;
    case TUESDAY -> 7;
    case THURSDAY, SATURDAY -> 8;
    case WEDNESDAY -> 9;
};
```

Here, `switch` directly returns a value assigned to `numLetters`. The arrow (`->`) syntax eliminates fall-through and `break` statements.

### `yield` keyword (for complex logic)

If a case requires more than one statement, we can use a block with the `yield` keyword.

```java
int result = switch (operation) {
    case "ADD" -> {
        int sum = a + b;
        yield sum; // returning value from block
    }
    case "SUBTRACT" -> a - b;
    default -> throw new IllegalArgumentException("Unknown op: " + operation);
};
```

The `yield` keyword returns a value from a case block — replacing the old `break` value pattern.

## 17. What is the main difference between a switch statement and a switch expression?

- **Switch statement:** executes code blocks but does not return a value.
- **Switch expression:** can return a value, making it usable in assignments or returns.

Example:

```java
// switch statement
switch (day) {
    case MONDAY: System.out.println("Start"); break;
}

// switch expression
String msg = switch (day) {
    case MONDAY -> "Start";
    default -> "Other";
};
```

## 18. What problem does a switch expression solve compared to old switch statements?

- Avoids accidental fall-through (no need for `break`).
- Supports multiple labels per case (e.g., `case MONDAY, FRIDAY ->`).
- Enables functional programming style, allowing expressions to yield a value.
- Reduces boilerplate and bugs.

## 19. How does the `yield` keyword differ from `return` or `break` in switch?

`yield` is used to return a value from a case block in a switch expression. You can't use `return` there (it exits the method), and `break` is not valid.

```java
int result = switch (op) {
    case "ADD" -> {
        int r = a + b;
        yield r; // correct
    }
    default -> 0;
};
```

### Old switch vs new switch expression

| Feature | Old Switch | New Switch Expression |
| --- | --- | --- |
| Returns value | No | Yes |
| Requires `break` | Yes | No |
| Arrow syntax | No | Yes |
| Fall-through | Yes | No |
| Exhaustive check | No | Yes (for enums/sealed types) |
| Pattern matching support | No | Yes (Java 17+) |

## 20. What does "exhaustive check" mean?

In a switch expression, the compiler requires that all possible input cases are covered. If not, compilation fails, unless you include a `default` branch.

This is different from the old switch statement, which didn't care — it could compile even if you missed cases.

### Example 1 — Non-exhaustive switch (compile error)

```java
enum Day { MONDAY, TUESDAY, WEDNESDAY }
String msg = switch (Day.MONDAY) {
    case MONDAY -> "Start";
    case TUESDAY -> "Second";
    // Missing WEDNESDAY!
};
```

Compilation error:

```text
The switch expression does not cover all possible input values.
```

To fix it, either:

```java
// Option 1: Add missing case
case WEDNESDAY -> "Midweek";
// Option 2: Add default
default -> "Other";
```
