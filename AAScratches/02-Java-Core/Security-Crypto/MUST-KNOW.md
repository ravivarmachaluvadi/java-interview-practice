## Full practice order


### A — Building blocks

- `A01_CaesarCipher.java` — Modular shift substitution cipher
  - The zero-dependency mental model of encryption - key = shift, decrypt = inverse shift, symmetric by construction - and it is the only file here you can reason about without the JCE API, so it comes first.
- `A02_AESExample.java` — AES symmetric encryption via JCE **[must-know]**
  - Teaches the Cipher/SecretKeySpec/doFinal/Base64 pipeline that RSAExample reuses verbatim, and it is the file whose flaws (ECB mode, hardcoded 16-byte key, no IV) are the actual staff-level interview conversation about encrypting data at rest.

### C — Medium

- `C01_RSAExample.java` — RSA key pair encrypt/decrypt
  - Assumes the Cipher lifecycle from AESExample and adds the non-obvious parts - key pair asymmetry, the block-size ceiling that forces hybrid encryption, and encryption vs signing - so it sits after the symmetric work.

## Interview readiness

This folder is a beginner's tour of encryption, not a senior engineer's crypto toolkit. Three files cover exactly one axis — confidentiality — and they cover it in the form an interviewer treats as a red flag: AESExample.java calls Cipher.getInstance("AES"), which silently resolves to AES/ECB/PKCS5Padding, with the key hardcoded as the literal String "1234567890123456"; RSAExample.java calls Cipher.getInstance("RSA"), which resolves to PKCS#1 v1.5 padding rather than OAEP. Both would fail a security review at any product company, and a staff interviewer will open with exactly that observation. More importantly, the other half of applied cryptography is completely absent from the folder and from the whole scratches workspace — I grepped every .java file under AAScratches for MessageDigest, Mac, Signature, KeyStore, SecureRandom, GCMParameterSpec, IvParameterSpec, PBKDF2 and BCrypt, and the only hits are an unrelated MerkleTreeExample and a string-match in a design-patterns file. That means there is no hashing, no integrity, no authenticity, no key management and no randomness anywhere: he currently cannot answer "how do you store passwords", "how do you verify this webhook actually came from Stripe", "sign this payload so the receiver knows it is from us", or "where does the AES key live in production" with working code. The gap is not depth on what he has — it is that roughly two-thirds of the canonical interview surface for this topic is untouched. Fixing the top five items below (GCM, password hashing, HMAC, signatures, envelope encryption) would move this folder from screening-level to genuinely senior in about a day of work, because each one is a short file and the JCE lifecycle he already knows carries straight over.

## Gaps — canonical problems NOT in this folder

| Priority | Problem | Technique | Why it matters |
|---|---|---|---|
| high | AES-GCM authenticated encryption with a random per-message IV | Cipher.getInstance("AES/GCM/NoPadding") with GCMParameterSpec(128, iv), a fresh 12-byte SecureRandom nonce per message, IV prepended to the ciphertext, plus a tamper test that flips one byte and shows AEADBadTagException on decrypt. Alongside it, an ECB-vs-CBC-vs-GCM comparison that encrypts a repeating plaintext under ECB and prints the identical ciphertext blocks. | This is the single highest-value gap. His only AES file uses ECB with a hardcoded key, and 'why is ECB wrong, what would you use instead, and what does the IV do' is the most predictable follow-up in the entire topic. Without GCM he also has no answer to 'how do you know the ciphertext was not modified in transit' — encryption alone gives confidentiality, not integrity, and that distinction is what separates a junior from a senior answer. |
| high | Password storage: salted hashing with PBKDF2 (and BCrypt/Argon2 as the comparison) | SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256") with a per-user 16-byte SecureRandom salt and a high iteration count, storing algorithm+iterations+salt+hash in one encoded string, and verifying with MessageDigest.isEqual for constant-time comparison. Contrast against BCrypt's built-in salt and cost factor. | 'How do you store user passwords' is asked in virtually every backend interview, and the expected answer is the opposite of everything in this folder: you do not encrypt passwords, you hash them, one-way, salted, and deliberately slow. He currently has no hashing code at all, so he has nothing to reason from about salts, work factors, rainbow tables, or why a plain SHA-256 of a password is still wrong. |
| high | HMAC request/webhook signing and verification | Mac.getInstance("HmacSHA256"), init with a SecretKeySpec shared secret, sign a canonical string (timestamp + body), verify on the receiving side with MessageDigest.isEqual rather than String.equals, and reject stale timestamps to block replay. | This is the most common real-world crypto task at a product company — verifying Stripe/GitHub/Twilio webhooks and signing internal service-to-service calls. It also forces the three-way distinction interviewers probe: a hash proves nothing about who sent it, an HMAC proves the sender knew a shared secret, a signature proves it with a key the verifier does not have. The constant-time comparison detail is a classic 'did he actually do this in production' tell, because String.equals leaks via timing. |
| high | Digital signatures: sign with the private key, verify with the public key | java.security.Signature with SHA256withRSA and SHA256withECDSA — initSign/update/sign on one side, initVerify/update/verify on the other, plus a test that mutates the message and shows verify() returning false. | He has RSA encryption but not RSA signing, and interviewers deliberately test whether a candidate confuses them: encryption uses the recipient's public key, signing uses the sender's private key, and the two directions answer completely different questions (secrecy versus provenance and non-repudiation). Signatures are also the foundation of TLS certificates, JWT RS256 and code signing, so the gap blocks several follow-up conversations at once. |
| high | Hybrid (envelope) encryption: AES data key wrapped with RSA-OAEP | Generate a random AES-256 key with KeyGenerator, encrypt the payload with AES/GCM, then encrypt just that data key with Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding") and ship the wrapped key next to the ciphertext. Decrypt by unwrapping the key first. | His own notes flag this as deliberately left open, and it is the answer to the question his RSAExample invites: 'now encrypt a 10 MB file with that RSA key.' RSA cannot do it — a 2048-bit key encrypts at most ~245 bytes with PKCS#1 padding — so the real-world pattern is always hybrid. This is also literally how AWS KMS, GCP KMS and every disk-encryption scheme work, which makes it the bridge from this folder into system-design answers about key rotation and data-key caching. |
| high | Proper key, IV, salt and token generation with SecureRandom and KeyGenerator | KeyGenerator.getInstance("AES").init(256) for real keys, SecureRandom for IVs, salts and session/reset tokens (Base64url-encoded), and a side-by-side demo showing java.util.Random with a fixed seed reproducing the exact same 'random' token twice. | His AESExample derives an AES key from the literal string "1234567890123456", which is the exact bug an interviewer will point at first, and the follow-up is always 'so where should the key actually come from?' Predictable randomness is a real and frequently-exploited vulnerability class — password reset tokens and session IDs generated from java.util.Random or System.currentTimeMillis are guessable. He needs a file that makes the correct source of randomness reflexive rather than something he reasons about on the spot. |
| medium | SHA-256 message digest and file integrity checksum | MessageDigest.getInstance("SHA-256"), streaming a file through DigestInputStream, hex-encoding the digest, and comparing against an expected checksum. Include a short note on why MD5 and SHA-1 are retired (practical collisions) and what avalanche and preimage resistance mean. | Hashing is the primitive underneath password storage, HMAC, signatures, Merkle trees and blockchain, and he has no MessageDigest code anywhere in the workspace. It is also the setup for the most basic sorting question in the topic — 'is hashing encryption?' — where the expected answer is that hashing is one-way and fixed-length with no key, so there is no 'decrypt'. Medium rather than high only because the PBKDF2 and HMAC work above will cover most of the same conceptual ground. |
| medium | Key management: loading keys from a KeyStore instead of hardcoding, with versioned keys for rotation | Create a PKCS12 keystore with keytool, load it via KeyStore.getInstance("PKCS12") with a password from an environment variable, pull out a SecretKey or PrivateKey, and tag ciphertext with a key ID so old data stays decryptable after a rotation. | Every senior-level crypto interview ends at 'where does the key live and what happens when it leaks?' — and a hardcoded string in source control, which is what this folder currently demonstrates, is the wrong answer. Knowing the keystore/KMS path, the envelope-with-key-id pattern for rotation, and the difference between a truststore and a keystore also unlocks the adjacent TLS and mutual-TLS discussion, which is otherwise unreachable from what he has. |
