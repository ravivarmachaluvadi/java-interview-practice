## Full practice order


### A — Building blocks

- `A01_SnowflakeIdGenerator.java` — Bit-packed time-ordered distributed IDs **[must-know]**
  - Identity comes first: sharding, sort order and keyset pagination in every later design assume a unique monotonic key already exists.
- `A02_WideColumnStore.java` — Column-family / row-key data model **[must-know]**
  - The store those IDs are written into — partition-key plus clustering-column thinking that every Cassandra or DynamoDB answer later leans on.

### C — Medium

- `C01_MerkleTreeExample.java` — Hash tree for replica diffing
  - Assumes replicated rows already exist (from the wide-column model); teaches cheap detection of which subtree diverged before you discuss repairing it.

### D — Hard

- `D01_ErasureCodingExample.java` — XOR / Reed-Solomon parity blocks
  - Last because it only makes sense once 3x replication is the assumed baseline; the parity-algebra insight buying the same durability at ~1.5x overhead is non-obvious.

## Interview readiness

This folder is about 25% of the way to staff-ready, and its four problems cluster suspiciously tightly: Snowflake, wide-column, Merkle and erasure coding are essentially four pages of the Dynamo/Cassandra paper — ID generation, data model, anti-entropy, durability. That is a coherent theme, but it means a single interviewer probe in the same territory ("how do keys get assigned to nodes in the first place?") lands on empty space, because the partitioner — consistent hashing — is the one Dynamo pillar he has not written. The other structural gap is that everything here is a write-path or storage primitive; there is no code at all for the request-path primitives every product-company loop opens with (rate limiting, idempotency, caching under concurrency, backpressure), even though his notes folder discusses Saga, payments and quorum at length. Quality is also uneven in a way an interviewer will catch on the first follow-up: MerkleTreeExample computes a root but has no tree-diff or proof-verification, so it cannot actually do the job Merkle trees exist for (comparing two replicas to locate divergent key ranges) — he can explain the idea but not demonstrate it; ErasureCodingExample is XOR-only with a single parity, so it dies on the standard "now lose two of six fragments" follow-up; WideColumnStore is a nested HashMap with no sorted clustering columns, no partitioning and no flush/compaction path, so "walk me through what Cassandra does on disk" has no code behind it. Net: he can hold a 20-minute conversation about replication and storage, but he currently could not whiteboard a partitioner, a limiter, a conflict resolver or an idempotent write — and those are the four things most likely to be asked.

| high | Bloom filter (with false-positive math and a counting variant) | Bit array plus k independent hashes derived by double hashing, sizing from m = -n*ln(p)/(ln2)^2 and k = (m/n)*ln2, measured false-positive rate, counting Bloom filter for deletes | The canonical 'save an expensive lookup' primitive and a direct follow-up to work he already has. What gets probed is not the bit array but whether he can pick m and k from an expected n and target p, and state clearly that false positives are possible while false negatives are not — and that deletes are impossible without the counting variant. That is a 25-minute exercise he has not done. |
| high | Vector clocks / version vectors with conflict detection and resolution | Map of nodeId to counter per value, increment on local write, merge on replication, compare for descends-from / concurrent, surface siblings, then contrast with last-write-wins on a physical timestamp and with Lamport clocks | This is the exact next question after his Merkle tree and he has nothing for it. He also needs this to answer 'why is last-write-wins dangerous under clock skew', which connects straight back to the clock-skew branch he already wrote in SnowflakeIdGenerator. Writing the comparison logic is the only way the concurrent-vs-causal distinction becomes sayable under pressure. |
| high | Idempotency key store and transactional outbox (exactly-once effects) | Idempotency-key table with a unique constraint and stored response, request fingerprint to detect key reuse with a different body, in-flight vs completed states for concurrent retries, plus an outbox table written in the same local transaction and drained by a relay to the broker | Highest-value product-company gap, and the one his own notes set up without code: he has Payment_System_Design.md and Distributed_Transactions_Saga_QA.md but no implementation.
