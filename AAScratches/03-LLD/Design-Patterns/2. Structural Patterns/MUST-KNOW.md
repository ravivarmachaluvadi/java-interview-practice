# 2. Structural Patterns — must-know order

**Techniques in this topic:** Wrap-and-delegate: hold a reference to another object and forward calls — the single primitive underneath Adapter, Decorator, Proxy and Facade, Same-interface wrapping: when the wrapper implements the wrapped type, wrappers stack recursively (Decorator chain) and become drop-in substitutes (Proxy), Composition over inheritance: avoiding the combinatorial subclass explosion, either by stacking wrappers (Decorator) or by splitting one hierarchy into two (Bridge), Uniform interface over part-whole structures: treating a leaf and a container identically so client code recurses without type checks (Composite), Intent vs structure: Adapter, Decorator and Proxy are near-identical in code and differ only in purpose — being able to say which one you are using and why is the interview signal, Indirection as a control point: a wrapper is where you put access control, lazy initialisation, caching, logging and remoting without touching the real class (Proxy, the basis of Spring AOP and Hibernate lazy loading), State partitioning for memory: splitting intrinsic (shared, cached by a factory) from extrinsic (per-instance, passed in) state (Flyweight), Subsystem encapsulation: one coarse entry point that orchestrates several fine-grained services, the everyday shape of a service-layer facade

## Full practice order


### A — Building blocks

- `A01_AdapterPatternDemo.java` — Wrap-and-delegate behind target interface **[must-know]**
  - The atom of every other file here — hold a reference to an incompatible object, implement the interface the client expects, translate in between; Decorator, Proxy, Facade and Bridge are all variations on this one move.

### B — Easy

- `B01_FacadePatternExample.java` — One entry point over a subsystem
  - The degenerate case of delegation — aggregate several collaborators, no shared interface, no polymorphism — so it is the easiest warm-up and nothing later depends on it, but it is also the pattern you already write daily as a service layer.

### C — Medium

- `C01_DecoratorDesignPattern.java` — Stackable same-interface wrappers **[must-know]**
  - Takes Adapter's delegation and adds the key constraint — the wrapper implements the same interface as the wrappee — which is what makes wrappers stack; this recursion is the idea Proxy and Composite both assume.
- `C02_ProxyDesignPattern.java` — Substitutable wrapper controlling access **[must-know]**
  - Structurally identical to Decorator, so it must come after it; the new content is intent and lifecycle — the wrapper owns creation (lazy init) and gates calls, which is exactly how Spring AOP and Hibernate lazy loading work under a Java staff interview.
- `C03_CompositePattern.java` — Recursive tree, uniform leaf/node interface
  - Generalises the linear wrapper chain into a tree — a node holds many children rather than one wrappee — and adds the transparency-vs-safety trade-off of where add/remove lives, which is the follow-up interviewers actually push on.
- `C04_FlyweightExample.java` — Intrinsic/extrinsic split with interning factory
  - Assumes Composite's context-object-referencing-shared-object shape and adds the memory insight: cache the invariant part in a factory, pass the varying part per call — mechanical once seen, but the state split is the part candidates miss.

### D — Hard

- `D01_BridgePatternExample.java` — Two hierarchies varying independently
  - Hardest here because the insight is upstream of the code — recognising two orthogonal dimensions of change and refusing the cartesian-product subclass explosion — and because you must defend why it is not just Strategy or Adapter, which only lands after both of those are solid.

## Interview readiness

Pattern coverage here is complete — all seven GoF structural patterns are present (Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy), each implemented correctly and idiomatically with a clear intent comment at the top. That clears the screening bar: if an interviewer asks "explain Decorator and code it", he is fine. The weakness is that every file is the same artifact — a 40-90 line single-file textbook demo in a toy domain (coffee with milk, trees on a map, a product bundle, online-vs-instore payment) with no JDK or framework grounding, no concurrency or lifecycle concerns, and no problem statement ambiguous enough that he has to *choose* a pattern rather than illustrate a named one. Senior and staff loops rarely ask "implement Decorator"; they ask "how does @Transactional actually work and why does calling it from within the same class do nothing", "add retries and caching to this client without touching it", "we're integrating three payment gateways, design the boundary", "design an in-memory file system" — and they score the follow-ups: intent discrimination, thread-safety, unbounded growth, ordering, what happens when the wrapped type can't satisfy the wrapper's contract. He has the vocabulary and none of the war stories. Two concrete tells a staff interviewer would seize on: ProxyDesignPattern.java is a hand-written static proxy with no mention of java.lang.reflect.Proxy or CGLIB, and FlyweightExample.java's factory is a plain static HashMap with computeIfAbsent — not thread-safe, unbounded, and never cleaned up, which is exactly the question that follows "nice, now put this in a web server". Fixing the eight gaps below is mostly a matter of re-staging patterns he already knows onto harder problems, so this is maybe two to three evenings of work, not a rebuild.
